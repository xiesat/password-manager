# 局域网同步协议 (SYNC PROTOCOL v1)

> 无云服务器，桌面端与移动端在**同一局域网**内直连同步。
> 参考实现：`sync_service.py`；测试：`tests/test_sync_service.py`。

---

## 1. 设计前提

| 事实 | 结论 |
|---|---|
| 交换的是整库密文 `v3:<base64>`（AES-256-GCM） | 链路上**不出现明文**，因此不需要 TLS 提供机密性 |
| 需要防的是"中间人替换密文"和"重放旧库" | 用**配对令牌 + HMAC 签名 + 时间戳 + nonce** 提供认证与防重放 |
| 无需证书体系 | 不引入 CA/自签证书，降低移动端实现成本 |

> ⚠️ 令牌必须通过**带外信道**传递（本机屏幕上的二维码/配对文本），绝不在 HTTP 中明文传输。

---

## 2. 配对信息（二维码内容）

主机在界面上展示一段 JSON，同时渲染为二维码：

`@jsonc
{
  "protocol": 1,
  "host": "192.168.1.23",     // 主机局域网地址
  "port": 8765,                // 主机监听端口（0 表示系统分配）
  "token": "<43 字符 urlsafe base64，256bit 随机>",
  "vault_id": "<32 位 hex>",   // 必须是同一个库，否则拒绝连接
  "device_id": "<8 位 hex>",
  "device_name": "DESKTOP-XXX"
}
`@

客户端扫描/粘贴后即可连接。`vault_id` 用于防止"连到了另一个人的库"。

---

## 3. 认证

`@text
auth_key = HKDF-SHA256(ikm = token, salt = vault_id, info = "pm-sync-auth-v1", L = 32)
`@

每个请求携带：

| Header | 说明 |
|---|---|
| `X-PM-Timestamp` | 毫秒时间戳 |
| `X-PM-Nonce` | 随机 ≥16 字节的 hex，单次使用 |
| `X-PM-Signature` | `HMAC-SHA256(auth_key, timestamp \n nonce \n METHOD \n PATH \n sha256(body))` |

服务端校验顺序：时间戳在 **±120 秒**窗口内 → nonce 未被使用过 → 签名匹配（常量时间比较）。
任一步失败返回 **401**，且**不区分具体原因**（避免给攻击者提示）。

**响应也签名**：服务端用同样的方式对响应体签名（`METHOD = "RESPONSE"`），客户端校验，实现双向认证。

---

## 4. 端点

### `GET /info`
无需认证，用于确认对端与版本：

`@json
{"protocol": 1, "vault_id": "...", "device_id": "...", "device_name": "..."}
`@

### `GET /vault`（需认证）
用于新设备**首次加入**：下载主机的整库密文。
签名按 `method="GET", path="/vault", body=空` 计算；响应同样被签名。

`@json
{"vault": "v3:<base64 整库密文>", "vault_id": "...", "device_id": "...", "device_name": "..."}
`@

客户端用用户输入的**同一个库密钥**解密后保存为本机库，即完成"加入"。
主机未开放下载时返回 400；未通过认证返回 401。

### `POST /sync`
请求体：

`@json
{"vault": "v3:<base64 的整库密文>"}
`@

响应体（200）：

`@json
{
  "vault": "v3:<base64 的合并后整库密文>",
  "conflicts": [
    {"kind": "both_modified", "name": "Google 账号", "copy_id": "<uuid>"}
  ],
  "vault_id": "...",
  "device_id": "..."
}
`@

错误：`400` 请求体不合法；`401` 认证失败；`404` 路径不存在。

---

## 5. 谁做合并

### 首次加入（bootstrap）

新设备上还没有库，此时**不能走合并**（空库会被当作"对端删除了所有记录"）。
正确流程是先用 `GET /vault` 把主机的库**整份下载**下来，再用同一个密钥解密保存，
之后两端才处于"同一个库"的状态，后续同步才走下面的合并流程。

### 日常同步

**主机做合并**，客户端采用结果：

`@text
客户端 ── POST /sync {自己的整库密文} ──▶ 主机
                                         ├─ 用会话密钥解密客户端密文
                                         ├─ merge_remote() 三方合并进本机
                                         ├─ 原子写回本机 .sk
                                         └─ 返回「合并后的整库密文」
客户端 ◀── 200 {合并后的整库密文, 冲突列表} ──
   ├─ 校验响应签名
   ├─ 用同一密钥解密并校验可解
   └─ 原子写回本机 .sk，重载界面
`@

由于两端使用**同一个库密钥**，且合并规则是确定性的（见 `VAULT_FORMAT.md` §6），
两端最终得到**相同内容**（可用 `content_hash` 校验）。

---

## 6. 防重放与防回滚

- **重放**：时间窗 + nonce 去重，重放同一请求直接 401（已测试）。
- **回滚**：三方合并以 `sync_base` 为基准，
  陈旧的对端内容会被判定为"与 base 相同"而不覆盖本机改动；
  即使内容被误判为冲突，也只会**多保留一个版本**，不会丢数据。

---

## 7. 安全注意事项

1. **令牌即密码**：拿到配对文本即可与该主机同步，请勿截图外发；同步结束后关闭窗口即停止服务。
2. **仅监听局域网**：服务默认绑定 `0.0.0.0:8765`，同网段可达。首次启动 Windows 防火墙会询问，请选择"专用网络"。
3. **明文只存在于内存**：网络上是密文；解密与合并发生在两台已解锁的设备内存中。
4. **主机必须已解锁**：未输入密钥时无法启动同步。
5. **不传递密钥**：两端必须各自已持有同一个库密钥，协议不传输密钥。
6. 当前版本为**单次同步**：主机窗口关闭即停止监听，不常驻后台。

---

## 8. 移动端实现清单（Android）

1. 解析二维码 JSON，校验 `protocol == 1`；
2. `HKDF-SHA256` 派生 `auth_key`（RFC 5869，测试向量见 `VAULT_FORMAT.md` / 本协议 §3）；
3. 用 SHA-256 + HMAC 生成签名头，发送 `POST /sync`；
4. 校验响应签名，解密返回的密文，三方合并（同一套 `spec/merge_vectors.json`），原子落盘；
5. 平台注意：Android 需 `INTERNET` 权限；局域网地址可能随 Wi-Fi 变化，需重新扫码。
